## 1. Live Read-Only Account Verification

- [ ] 1.1 Obtain explicit operator approval to run against the live Production account, and confirm the launch environment carries a complete `BFK`/`BFS` pair and the proxy variables whose egress address matches the key's IP restriction.
- [ ] 1.2 Start the application, select the Futures workspace, and record which of balances, positions, regular orders, ALGO orders, and the user-data stream reach `ready` — step 1, «Деск поднимается на Futures», in `verify-the-desk-in-one-sitting/runbook.md`.
- [ ] 1.3 For any resource that does not reach `ready`, record the sanitized category and code shown in the ticket, and determine whether the cause is credentials, key permissions, IP restriction, or the endpoint itself — the same step 1, which states the reading that separates the three: a code on all five is credentials, key rights or the IP restriction; a code on ALGO orders alone is the ALGO endpoint or its permission. That step also carries the ALGO answer forward, because step 33 cannot be run without it.
- [ ] 1.4 Confirm account-wide order visibility: orders on a symbol other than the selected one remain listed after switching symbols — step 23, «Ордера на других контрактах остаются в списке».
- [ ] 1.5 Confirm no order was placed, amended, cancelled, or closed during the verification. **This is why step 23 tells the operator not to place an order if one is already working on another contract:** the observation needs *an* order on a second contract, not a new one, and the runbook only places one so the pass does not depend on what the operator happens to have open. If it does place one, this item is answered "one order placed to stage 1.4, cancelled in the same step" rather than checked — the two are not the same claim, and the difference belongs in the ledger.
- [ ] 1.6 Record the outcome in `docs/futures_trading.md` if it changes any documented operator expectation.
